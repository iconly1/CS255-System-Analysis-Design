# CS 255 DriverPass Project

## Project Summary

DriverPass was the client for this project. They wanted a system that would help students prepare for their driving tests through online practice tests, training materials, and on-the-road driving lessons. The system also needed to handle customer accounts, training packages, scheduling, drivers, vehicles, payments, and student progress.

## What I Did Well

I think I did well taking the needs from the DriverPass interview and turning them into an actual system design. Instead of only listing what the system needed to do, I used UML diagrams to show how users interact with the system, how different processes flow, and how the main parts of the system connect. I also tried to keep the design focused on what DriverPass actually needed instead of adding features just because they could be added.

## What I Would Improve

If I could revise one part of the project, I would improve my UML class diagram. I would add more detail to some of the relationships, including multiplicities such as one-to-one or one-to-many. This would make it easier for another developer to understand exactly how the different classes and records relate to each other.

## Understanding the User's Needs

I started by looking at what DriverPass wanted customers and employees to be able to accomplish. Customers needed to register, purchase training packages, take practice tests, view their progress, and schedule driving lessons. Employees needed tools for scheduling, managing customers, viewing lessons, and maintaining the system. I used those needs to guide the use case, activity, sequence, and class diagrams.

Considering the user's needs is important because a system can work technically and still fail if it does not solve the problem the user actually has. The requirements should drive the design instead of making the user adjust to whatever was easiest to build.

## My Approach to Software Design

My approach is to understand the problem first and then break the system into smaller pieces. I like to identify the users, the tasks they need to complete, the information the system needs to store, and the decisions that happen during each process. From there, UML diagrams help me look at the same system from different angles before development begins.

In future projects, I would continue using requirements gathering, use cases, activity diagrams, sequence diagrams, and class diagrams to organize the design. I would also review the diagrams against the original requirements throughout the process so that the design does not slowly drift away from what the client asked for.
